# RFC: Bucket transfer between providers (Draft)

> **Draft — needs triage.** Analysis and proposal, **not implemented**. Written
> against `dev` at 67ce0738 (2026-09-11). File and line references point at
> that state. Design changes go through a `docs/design/` PR per
> `.github/CODEOWNERS`.

## Story

A dApp operator owns bucket `B`. The dApp's users write into `B` through the
dApp (as bucket `Writer` members, through a shared writer key, or through a
`pallet_revive` contract). The data in `B` is generated by those users on their
own clients. The operator never had a local copy and cannot ask the users to
upload it again: they may be gone, offline, or unaware that the bucket exists.

`B` has one primary provider `P1` under a 1-year agreement. Before it expires,
the operator needs `B` to continue on provider `P2`:

1. `P2` must become a **primary** of `B`. Replicas are read-only, and the dApp
   keeps writing.
2. `P2` must obtain the full content of `B` from `P1` or from any replica,
   **without the operator or the users re-uploading**.
3. The operator needs on-chain evidence that `P2` has the data before `P1`'s
   agreement ends.
4. `bucket_id`, the members list, the snapshot history, drive ids and every
   external reference must remain valid.

The same story with different triggers: `P1` winds down (#281), `P1` blocks
extensions or raises prices, `P1` is slashed, or the operator wants a second
primary for redundancy and later drops the first.

## What the design specifies

Statements that apply to the story, with source sections.

**Multi-primary buckets exist.** Design doc, "Buckets: Stable Identity in a
Fluid Provider Market": primaries are "Added only by bucket admin", "Receive
writes directly from clients", "Count toward `min_providers`", "Limited to ~5
per bucket". The "Personal Backup" and "Media in Chat" use cases both start
with "Add 2-3 diverse providers" or "1-2 providers" on one bucket. The design
assumes a bucket can have several primaries and that the admin adds them.

**No join flow is specified.** Implementation doc, "Provider Lifecycle in
Bucket", has one flow for a primary: `establish_storage_agreement` creates the
bucket with that provider as its single primary. Nothing describes how a
second primary joins an existing bucket, how it obtains the data, or when it
becomes liable.

**Primaries do not sync with each other.** Implementation doc,
"Multi-Provider Coordination (Primary Providers)", lines 108-121:

> Primary providers don't sync with each other. Clients are responsible for
> uploading to each primary provider they want to store their data.
> [...]
> 4. Primaries not in the snapshot should sync (client re-uploads)

This is the statement the story contradicts: the client cannot re-upload.

**Replicas sync autonomously and are read-only.** Same section: "Replica
providers sync autonomously from primaries or other replicas. They confirm
sync on-chain and are liable for the roots they've confirmed." Replicas never
receive writes, never count toward `min_providers`, cannot be
early-terminated, and the admin has no control over them.

**Liability follows signatures.** Same section: "A provider is only liable
for MMR states they acknowledged (signed). Challenges against the canonical
checkpoint only work for providers listed in the snapshot's provider
bitfield." A primary that never signs is paid and never slashable.

**Agreements are binding to expiry; continuation is `extend_agreement`.**
Design doc, "Storage Agreements", "Binding commitment"; implementation doc,
`extend_agreement`. No auto-renew, no prepaid multi-period pool. Permissionless
extension exists only while the provider's price is at or below the locked
price and extensions are not blocked.

**At expiry the provider is released.** Implementation doc, "Agreement
expiry": "Provider is no longer bound to store data". No retention window is
specified. The same section also states "Providers remain liable for snapshots
they signed until those snapshots are superseded", which the code does not
implement after expiry (see "Retention after expiry").

**Ownership transfer is a different thing.** Implementation doc,
`transfer_agreement_ownership`: changes the owner account of one agreement
(sell a slot, hand to a DAO). Same provider, same bucket. It moves the payer,
not the provider or the data.

**Private buckets restrict sources.** Design doc, "Bucket Visibility &
Access": primaries on a private bucket serve reads only to members; "Provider
accounts are not members, so on a private bucket a freeloader's only honest
source is a replica." A joining primary is in that position.

## Direction

Make "primary" a role the admin can add to an existing bucket, and let a
joining provider obtain the data from any current holder using the sync
protocol that replicas already use. The bucket is never transferred; the
provider set changes. The general form is "keep N agreements live, replace one
at a time". End-of-life migration is the N=1 case.

### Role transitions covered

| Leaver → joiner | Join path | Data path | Attestation | Missing today |
|---|---|---|---|---|
| Replica → Replica | `establish_replica_agreement` (exists) | replica sync (exists) | `confirm_replica_sync` (exists) | Coordinator fetches only from primaries; a bucket with no live primary cannot seed a new replica |
| Primary → Primary | none | none | signer bit via client-relayed `extend_checkpoint` | Join extrinsic, catch-up for the Primary role, provider-origin attestation, bitfield resize |
| Replica → Primary | none | replica already has the data | signer bit | Join extrinsic (Option A) or promotion (Option B) |
| Primary → Replica | `establish_replica_agreement` after the primary agreement ends | already local | `confirm_replica_sync` | Nothing. The same provider cannot have both roles at once (agreements keyed by `(bucket, provider)`) |

Role change on a live agreement is out of scope. The design treats agreement
role and terms as immutable; a role change is leave-then-join.

### Option A (recommended): join-primary extrinsic + role-independent catch-up

**On chain**

1. `add_primary_agreement(bucket_id, provider, terms, sig)`.
   - Origin: bucket admin. Primaries are admin-controlled by design and the
     admin is the owner of primary agreements (implementation doc,
     `end_agreement` note).
   - `terms` are provider-signed primary terms with `terms.bucket_id =
     Some(bucket_id)` and `terms.replica_params = None`.
     `establish_storage_agreement` already rejects `Some(_)`
     (`TermsBucketMismatch`), so `PRIMARY_TERM_CONTEXT` can be reused and a
     quote cannot be redeemed on the wrong path. Open question 2.
   - Shared validation skeleton from the implementation doc, "Storage
     agreements": owner match, `valid_until` window, signature, nonce replay
     window, provider active, `accepting_primary`, duration bounds, capacity,
     stake.
   - Additional checks: bucket exists; no agreement for `provider` on this
     bucket (`AgreementAlreadyExists`); `primary_providers.len() <
     MaxPrimaryProviders` (`MaxPrimaryProvidersReached` exists). Works on a
     bucket with zero primaries, which is how a bucket regains one (C1).
   - Effects: hold payment, push to `primary_providers`, insert
     `StorageAgreement { role: Primary, .. }`, update provider stats, emit
     `PrimaryProviderAdded { bucket_id, provider, owner, terms, expires_at }`.
   - Resize `snapshot.primary_signers` to cover the new index. `extend_checkpoint`
     also resizes instead of skipping.
2. Provider-origin attestation of the current snapshot. Either widen
   `extend_checkpoint` origin to "writer, admin, or a provider in
   `primary_providers` signing for itself", or add
   `confirm_primary_sync(bucket_id, signature)` that sets the caller's bit.
   Required, not optional: the story's operator may be offline, and without
   the bit the operator cannot even challenge `P2` (C2).
3. `finalize_agreement` already handles the leave side. No change.

**Provider node**

4. Catch-up duty for any agreement whose local MMR root differs from the chain
   snapshot root, regardless of role. Reuse `ReplicaSync::sync_from_primary`.
   Sources: every provider with a live agreement on the bucket, primaries and
   replicas. No sync payment for primaries; the storage fee covers it.
5. On catch-up completion, sign `CommitmentPayload::new(bucket_id,
   snapshot.commitment)` and submit it (step 2), or expose it on
   `GET /checkpoint-signature` for client relay as a fallback.

**Client / SDK / UI**

6. "Add provider" and "Replace provider" flows in `@web3-storage/sdk`,
   drive-ui and s3-ui: discover a matching provider
   (`query_find_matching_providers`), negotiate over `POST /negotiate`, call
   `add_primary_agreement`, watch `P2`'s `/replica/sync_status` and its signer
   bit, then stop extending `P1`. Replace the `upload_replicated` stub.
7. Writers upload to all primaries from the moment `P2` is added (existing
   model). Catch-up covers the backlog. If a writer uploads to `P1` only, the
   catch-up duty re-fires on each checkpoint and `P2` lags by one checkpoint.
   For the dApp story this matters: the dApp's write path must read
   `primary_providers` from chain on each write, not a configured URL.

**End-to-end flow**

```
operator/client              chain                        P1              P2
  |  negotiate terms (bucket_id=B) ------------------------------------->  |
  |  <------------------------------------------------- signed terms ----  |
  |  add_primary_agreement(B, P2, terms, sig) -->|                          |
  |                                   primary_providers = [P1, P2]         |
  |                                   primary_signers resized              |
  |                                              |   catch-up: read snapshot root
  |                                              |   <-- /mmr_peaks, /fetch_nodes -- P2
  |                                              |   P1 --> nodes ------------> P2
  |                                              |   P2 verifies against chain root
  |                                              |   P2 --> confirm_primary_sync --> bit set
  |  (optional) challenge_checkpoint(B, P2, target) --> P2 responds        |
  |  dApp writes go to P1 and P2 until T                                   |
  |  at T: end_agreement(B, P1) / claim_expired --> P1 removed, bit cleared
  |                                   primary_providers = [P2]
```

Every node `P2` fetches is verified against the on-chain root, so `P1` cannot
feed `P2` wrong data. `P2`'s liability starts when its bit is set. Before that
it is paid but not slashable, the same as a fresh primary today between
agreement start and first checkpoint.

### Option B: replica first, then promote

Open a replica agreement with `P2` (exists), let it sync and
`confirm_replica_sync` (exists), then `promote_replica_to_primary(bucket_id,
provider, terms, sig)` converts the role with a fresh provider-signed primary
quote.

Pros: proof of possession is the existing `last_sync`; sync work is paid from
`sync_balance`; no provider-node change.

Cons: mutates a live agreement (duration, price, quota, role), which needs a
settlement of the replica part and a `sync_balance` refund inside one call;
contradicts "replicas run to expiry" even with both parties consenting; new
stats and event reasons; a replica that other replicas sync from disappears
from the replica set. More on-chain surface for the same result.

### Option C: client re-upload (status quo, not applicable)

The operator downloads from `P1` and uploads to `P2` via `/exists` +
`PUT /node`. Needs only the join extrinsic. It moves every byte through the
operator's client and assumes the operator can read all of `B`, which fails
for private per-user data the operator was never meant to read. Not a
solution for the story. Keep as a manual fallback for small public buckets.

### Why A

A adds one extrinsic, one attestation path and one provider-node duty, and
leaves agreement types immutable. B reuses more on-chain proof but has to
mutate a live agreement, which the design treats as invariant. A's proof (the
signer bit) is the instrument the design already uses for primary liability.

### Hints: turning a replica provider into a primary

Three ways to get from "P2 is a replica of B" to "P2 is a primary of B",
ordered by how much they need:

1. **Warm standby, then join (needs only Option A).** Keep a replica agreement
   with `P2` on `B` during the year. Before `P1` expires, let the replica
   agreement end and redeem a primary quote from `P2` via
   `add_primary_agreement`. The data is already local, catch-up is a no-op,
   attestation is immediate. Constraint: agreements are keyed by
   `(bucket, provider)`, so `P2` cannot have both roles at once. The replica
   agreement must end (expiry plus settlement, since `AgreementAlreadyExists`
   is checked on the record, not on liveness) before the primary one begins,
   which leaves a window where `P2` is not liable. Standing redundancy with
   one primary and one replica is therefore not seamless without one of the
   next two changes.
2. **Allow both roles for one provider.** Key agreements by
   `(bucket, provider, role)` or add a second map for replica agreements.
   Then `P2` can be joined as primary while its replica agreement continues,
   and the replica agreement expires on its own. Storage-layout change in the
   pallet, no new semantics.
3. **Promote in place (Option B).** `promote_replica_to_primary` converts the
   live replica agreement with a fresh primary quote. No liability gap, but it
   mutates a live agreement and needs a mid-term settlement of the replica
   part.

For the dApp story the recommendation is 1 plus 2: the operator funds a
replica of `B` from day one (the design's own redundancy answer), and joining
it as primary later costs one extrinsic and no data movement.

### Relation to multi-writer and multi-provider coordination

- **Multi-provider checkpoints** are the client-side Checkpoint Manager in
  `docs/drafts/CHECKPOINT_PROTOCOL.md` (provider discovery, commitment
  collection, consensus, conflict resolution). It reads `primary_providers`
  from chain, so a joined `P2` is picked up on the next checkpoint. It is the
  component that must deliver new writes to `P2` after the join (step 7).
  Related: #332 (`agreeing_providers` conflates root agreement with
  checkpoint signers), #388 (duplicate signer counting).
- **Multi-writer buckets** have no dedicated issue. The design covers them
  only in the "Media in Chat" use case ("Concurrent writes: content-addressed,
  parallel uploads don't conflict; commits coordinated via chat message
  ordering", design doc line 1036). #134 (dApps and mutable data) and #133
  (dApps integration story) are the closest. The story in this RFC adds a
  requirement to both: every writer's client must upload to every primary,
  so a writer that hard-codes `P1`'s URL keeps writing to the leaving
  provider. The dApp write path has to resolve primaries from chain per
  write, or the operator has to route writes through one component that
  does.
- **Membership bound**: `MaxMembers` = 100. A dApp with more users than that
  writes through a shared writer key or a contract
  (`docs/drafts/smart-contracts.md`), which makes the "one component that
  resolves primaries" shape the practical one.

## Gaps

### Transfer gaps

**G1. No way to add a primary to an existing bucket.** `P2` can only get a new
`bucket_id`, which breaks every reference (`bucket://<id>/...`,
`DriveInfo.bucket_id`, S3 bucket mapping, existing replicas of `B`). The
multi-primary shape exists on chain and has no extrinsic path.

**G2. No primary-to-primary data transfer.** The design assigns it to the
client. The provider-node sync loop exists and is gated to `Replica`. The sync
endpoints are role-agnostic, so only the trigger is missing.

**G3. No on-chain evidence for a joining primary.** Liability starts at the
signer bit. `extend_checkpoint` needs a writer/admin origin, so the provider
cannot attest alone, and the bitfield is sized at checkpoint time, so a later
joiner's bit is dropped silently.

**G4. Private buckets give the joiner no honest source.** Provider accounts
are not members. The admin must add `P2`'s account as `Reader` for the
transfer window, or a replica must exist. (The sync endpoints are
unauthenticated today, so the cooperative gate is not enforced; separate
drift.)

**G5. Layer 1 mirrors agreement fields.** `DriveInfo.expires_at` and
`max_capacity` are write-once copies of the first terms.

**G6. Overlap cost.** Both agreements are binding. The operator pays `P1` to
`T` and `P2` from the join block. Inherent to the model; document, do not fix.

**G7. Serving the bulk fetch is unpaid.** Read incentives are specified and
not implemented (#65 discussion). A provider winding down has weak incentive
to serve. Existing levers: the operator is an authorized challenger against
`P1` (cost split), and replicas are alternative sources.

### Continuity gaps

**C1. A bucket cannot regain a primary.** Once the sole primary expires, is
slashed or is early-terminated, `primary_providers` is empty and `checkpoint`
has no eligible signer. The bucket is read-only for the rest of its life.
Replicas keep serving what was checkpointed. G1 is the fix; the join extrinsic
must accept a bucket with zero primaries.

**C2. Paid is not liable for a second primary.** Nothing compels the second
primary to sign. With `min_providers = 1` a client can checkpoint with one
signature and the other primary is paid without proving possession. With
`min_providers = 2` one dead primary blocks all checkpoints until the admin
lowers `min_providers` or early-terminates it, which pays it in full. No
intermediate setting exists. The operator cannot challenge a primary whose
bit is unset. Provider-origin attestation (Option A step 2) is required.

**C3. Renewal needs a live, funded owner at a specific block.**
`extend_agreement` rejects an expired agreement (`lib.rs:1942-1945`). No
auto-renew, no prepaid pool. Missing the expiry block on the sole primary
triggers C1.

**C4. The provider has no notice obligation.** `set_extensions_blocked` and
`accepting_extensions = false` can be set one block before expiry. #281
covers the cooperative wind-down; nothing on chain enforces notice.

**C5. Just-in-time migration depends on the leaver.** Option A's catch-up
fetches from `P1`. If `P1` is the failing party, catch-up has no source unless
a replica exists. Standing redundancy is the shape that does not depend on the
leaver; the UI should recommend it for dApp buckets.

**C6. Layer 1 can end every agreement on a bucket, including third-party
replicas.** `delete_drive` → `cleanup_bucket_internal` ends all agreements
with pro-rated refunds and no role check. Contradicts "no early cancellation
for clients" (design doc, "Binding commitment") and "replicas cannot be
early-terminated" (implementation doc, `end_agreement`).

**C7. Replica attestation has a time window.** `confirm_replica_sync` must
match the current root or one of six historical positions, the oldest about
113 anchor blocks back. A replica of a large, frequently checkpointed bucket
may never confirm and is then never liable. A dApp bucket with many writers
is exactly that shape.

**C8. Nobody challenges automatically.** The design assumes background
spot-checks by client software ("Automation Removes the Human Factor"). Not
implemented. An offline provider stays paid until a human challenges, then
`ChallengeTimeout` (48h) passes before `remove_slashed`.

### Retention after expiry

No retention window exists. All three challenge extrinsics require
`anchor < expires_at`, so the provider is unchallengeable from the expiry
block and may delete immediately. The only exception is a challenge already
pending, which blocks settlement.

- `SettlementTimeout` (24h) is a payment window, not a migration window.
- "Snapshot liability remains until superseded" does not apply after expiry
  in code. Once the agreement record is gone, no challenge path finds it.
- The provider node has no deletion code, so data remains until the operator
  removes it. Nothing guarantees that.

A transfer must complete before `expires_at`. If the design wants a migration
window, the smallest form is a `RetentionPeriod` after `expires_at` during
which challenges stay valid and the agreement cannot be settled, priced into
the quote.

## Security and economics

- **Who can add a primary**: admin only. A compromised admin can already
  early-terminate primaries and add members; adding a primary spends the
  admin's own funds on one more agreement.
- **Bound**: `MaxPrimaryProviders` = 5 (`runtimes/web3-storage-local/src/storage.rs:94`).
  A replacement uses one extra slot temporarily.
- **Freeloading**: a joiner that fetches from peers behaves like a replica,
  which the design accepts. Its slashable obligation begins at the signer
  bit. A primary that never catches up is unpaid risk for the operator, not
  for the network.
- **Private buckets** (G4): admin adds `P2`'s account as `Reader` for the
  window, or relies on a replica.
- **Overlap payment** (G6): inherent; the UI shows it.
- **Unpaid egress** (G7): unchanged from replica sync today.
- **Replay**: the joining quote uses the same nonce window as any quote;
  `terms.bucket_id = Some(B)` binds it to the bucket.
- **`min_providers`**: unchanged. After `P1` leaves, a `min_providers` above
  the remaining count blocks checkpoints as today. The flow warns when
  `min_providers > 1`.

## Drifts found (flag, do not fix here)

1. `transfer_agreement_ownership` is specified in the implementation doc and
   absent from the pallet and `EXTRINSICS_REFERENCE.md`.
2. `extend_checkpoint` drops a signer bit whose index is beyond the stored
   bitfield and still emits `BucketCheckpointed` for that provider
   (`lib.rs:2180-2182`). Latent today; reachable once primaries can join.
3. Sync endpoints and `GET /read` are unauthenticated, while the design states
   primaries on a private bucket serve reads only to members (cooperative,
   not on-chain enforced). Filed as #383.
4. The provider node accepts `PUT /node` and `POST /commit` for any bucket a
   writer authenticates for, without checking that it has an agreement on
   that bucket, and initializes local buckets with an unbounded quota
   (`provider-node/src/api.rs:262-303`). A replica node therefore accepts
   writes it can never checkpoint. Quota part filed as #382; the missing
   agreement/role check is not filed.
5. `DriveInfo.expires_at` / `max_capacity` are write-once copies (G5).
6. `delete_drive` ends every agreement on the bucket early with pro-rated
   refunds, including third-party replicas (C6).
7. "Snapshot liability remains until superseded" does not apply after expiry:
   every challenge extrinsic requires a live agreement.
8. The design's use cases ("Add 2-3 diverse providers") assume a join path
   that the implementation doc never specifies and the pallet does not have.

## Open questions for the design owner

1. Provider-origin attestation: widen `extend_checkpoint` or add
   `confirm_primary_sync`?
2. Reuse `PRIMARY_TERM_CONTEXT` with `bucket_id = Some(_)` as the join
   discriminator, or introduce a `"primary-join-v1:"` context?
3. Amend "Primary providers don't sync with each other" to "primaries may
   catch up from any provider with a live agreement on the bucket; clients
   remain responsible for delivering new writes to every primary"?
4. Layer 1: derive mirrored agreement fields from Layer 0, or keep them and
   add update paths?
5. Is a pro-rated early exit for `P1` ever acceptable once `P2` has attested,
   or does the binding-commitment rule stay absolute? `delete_drive` already
   does this today (C6).
6. Should a `RetentionPeriod` after `expires_at` exist, during which the
   provider stays challengeable and the agreement cannot be settled?
7. Should a provider be required to announce a refused extension a minimum
   number of blocks before expiry (C4)?
