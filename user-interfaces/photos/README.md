# Photos — decentralized photo storage dApp

The UI keeps each user's photo library as files in the product's own bucket, through the TrUAPI
host's remote storage (`truapi.remoteStorage`): albums, photos with client-generated thumbnails, a
thumbnail grid, a full-resolution lightbox, and a crop/rotate editor. The host owns the bucket,
picks its provider, and asks the user to approve its plan.

A custom `Photos.sol` contract, exercised by the headless scripts, creates one **bucket** per user
through the storage-provider precompile `IWeb3Storage` (`0x…09010000`), is that bucket's admin,
grants the user a Writer role, and anchors the album-tree root CID on-chain. Design:
[`DESIGN.md`](./DESIGN.md).

## Layout

```
contracts/        Photos.sol + vendored IWeb3Storage.sol; build.sh → src/contract/Photos.json
scripts/lib/      TS helpers — PAPI deploy/call (contract.ts), /negotiate, libraryOf read +
                  setRoot (photos.ts)
scripts/          deploy-contract.ts, photos-flow.ts (run via tsx)
src/contract/     Photos.json (bin, generated by build:contract)
src/              React UI — state/ (chain, wallet: the host account, library: the storage
                  plan, album: the files, ui: open panels), lib/ (remote-library over
                  truapi.remoteStorage, host-account, host-chain-provider, chain-client,
                  chain-health, plans, group-by-day, edit-image, thumbnail; fs-root and
                  local-index for the headless scripts),
                  components/ (Header, Sidebar, PhotoGrid, Lightbox, PhotoEditor, PlanPicker,
                  PlanPanel, ProfileMenu, ChainStatus, Toasts), pages/Library.tsx (plan, then
                  the library)
```

## Quick start

Needs `solc` + `resolc` on PATH (see `examples/contracts/README.md`), and a running chain + provider.

```bash
cd user-interfaces && pnpm install

# terminals 1 & 2, from repo root:
just start-chain
just start-provider
just demo                 # register + accept the provider once

# build, deploy, run the headless flow (one namespaced entrypoint):
just photos build         # compile Photos.sol → src/contract/Photos.json
just photos deploy        # deploy; prints the contract H160
just photos flow          # deploy → createLibrary → album + photo → setRoot → verify
```

`just photos help` lists the actions. Each action also has a raw pnpm equivalent, e.g.
`pnpm --filter @web3-storage/photos build:contract`.

### Run the UI

The UI keeps its library in the remote storage of the TrUAPI host it runs in
(`truapi.remoteStorage`), so it runs only inside a host. Outside one it says so. With a local
chain and provider, run it through the CLI host with a stack that names the chain as its
`Web3Storage` role and the provider as its `storage-provider` service:

```bash
truapi-host dev --app-port 5178 --product-id photos.dot --stack <stack.json> -- pnpm dev
```

The host owns the account, the chain connection, the library's bucket, its provider and its
agreement, so the page has no network or account picker. The page reads the storage plan: with
none it shows the plans from `src/lib/plans.ts` (a size each, paid monthly or yearly), and the host
opens the bucket and asks the user to approve the price. A tier's price is the most the user pays;
the host may quote less. The plans stay available from the profile menu and the sidebar's storage
bar. Until payment is wired up in the host, the
bucket's account pays from its own balance, so fund it first: the host logs the account at debug
level when it opens the bucket. A plan whose funding ended shows as lapsed.

The library is plain files in the bucket's file tree: photo `/<Album>/<file>`, thumbnail
`/.thumbs/<Album>/<file>`, and an empty `/<Album>/.album` that keeps an album with no photos.
**Upload** (button or drag and drop) generates a downscaled JPEG thumbnail per photo (canvas,
longest edge ~320px) and stores the full photo plus the thumbnail. Uploads from the all-photos view
go into the `Camera roll` album. The grid renders from thumbnails, grouped by the day each photo
was stored, and clicking a photo opens it full-resolution in a lightbox with previous/next, rename,
delete (with undo) and a crop/rotate editor. The header's chain status opens the parachain's
connection state, best and finalized blocks, and the arrival delay of the last 48 blocks. Renaming stores the photo at its new path
and removes the old one. Writes run one at a time, since the host commits each on top of the root
it read. Any device of the user finds the same library: the host derives the bucket's account from
the user's seed and the product id.

The headless `photos-flow` below still exercises the contract flow (`contracts/`, `scripts/`); the
UI no longer uses the contract.

`photos-flow` asserts the contract account is the bucket admin, the user holds a Writer role on the
bucket, and `libraryOf(user)` reports the new bucket. It then uses the SDK's `FsTree` (mkdir an album,
PUT a multi-MB photo + a thumbnail), computes the bucket's metadata Merkle root **client-side**
(`metadataMerkleRoot` in `packages/core/src/merkle.ts`), anchors it via `setRoot`, and
verifies the locally recomputed root equals the on-chain anchor and that the bucket's file-system
root is the one the last write returned (plus a tamper check) — proving the control plane and the integrity anchor before any UI exists.
